## 四、改造建议（未实施）

### 4.1 按优先级

1. **修复 `MsgErrf` 变参缺陷（#9）**：`fmt.Errorf(format, f...)`；`MsgLogErrf` 一并修复。改动 1 行 + 回归。
2. **补全英文翻译（#10）**：为 196 码生成 `config/lang/en.csv`（可从 `MsgInfo` 反推中文 key，人工/工具批量翻译）。建议将 key 由中文改为稳定英文 ID（如 `err.param`），避免中文作 key 的脆弱性（现 `MsgByCode` 以中文为 key 查表）。
3. **语言归一化（#11）**：`GetAcceptLanguage` 或 `MsgByCode` 内做 `strings.SplitN(lang,"-",2)[0]` 映射（`zh`→默认中文、`en`→英文），使 `en-US/en-GB` 生效；未知语言回退 `zh-CN` 并打日志。
4. **P1 硬编码 8 处码化**：新增错误码（如 `AdminOnlyForbitCode`、`RateLimitCode`、`IpBlacklistCode`、`DbConnFailCode`、`WsCloseCode`），改为 `response.Error(c, code, lang.MsgByCode(code, lang.GetAcceptLanguage(c)))`。
5. **P2 内部 error**：aes/oss/permission/配置校验可保留纯英文（运维视角）或转码化；建议至少统一为英文避免日志乱码。
6. **UI 文案（#18-21）**：导出表头与根标签建议交由前端多语言（后端不下发中文文本），或入库字典后 `MsgByValue` 翻译；登录日志建议**落码不落文**（存 code+占位参数，展示时按语言渲染）。
7. **日志类（#22-24）**：保持中文即可，不做 i18n（i18n 只覆盖"返回给客户端的文本"）。

### 4.2 验证方式

- 请求头 `Accept-Language: en / en-US / zh-CN / fr`，抽查登录失败、限流 429、AdminOnly 403、service 各错误码返回的 `msg` 字段
- 回归：带参消息码（如 `DataQueryLogCode`）不再出现 `[…]` 与 `%!s(MISSING)`

## 六、结论

项目已具备"**错误码 + 语言参数 + CSV 翻译表**"的完整 i18n 骨架，**service 层（含本次新增 novel 模块）全部合规**；缺口集中在：

1. 中间件层 8 处硬编码 `gin.H`/`errors.New` 直达客户端（P1）
2. `MsgErrf` 变参 bug 使带参消息码文案损坏（P1，1 行可修）
3. 英文翻译覆盖 1.5% + 语言方言未归一化 → 英文切换实际不生效（P1）
4. 内部工具层 18 处中文 error（P2，运维可见）
5. 后台 UI 文案（导出表头/根标签/登录日志）未纳入多语言体系（P2）

按 4.1 顺序修复后，可实现"所有用户可见错误文本随 `Accept-Language` 切换"。
